A journal of actions and results

A journal of actions and results

Record the work, undo changes, inspect earlier states and continue an alternative analysis. This is a shared application capability, with a contract for every participating module.

The user requested a Git-like history of actions, results and errors in R19. This page specifies the proposed durable journal. The current browser experiment has in-memory undo/redo and snapshot files; it does not yet implement persistent event history, crash recovery or branches.

The template 0.2 editor now implements Trrack-backed saved states, named checkpoints, results and branches in a portable project file. Its failed automatic crash-recovery check is recorded separately; this does not complete every durable-journal requirement below.

Evaluate existing systems first

Trrack directly addresses branching interaction history. A bounded Node test of @trrack/core 1.6.1 passed action updates, undo/redo, branch traversal and serialization/import with error metadata and artifact references. ESM import passed; CommonJS loading failed on the tested Node 20.18.0 environment. This makes it a strong candidate for the interactive history layer, with a concrete packaging constraint.

AiiDA supplies scientific computation provenance and is a candidate when a complete workflow engine is justified. DVC supplies data/pipeline experiment tracking. Those two are documentation-reviewed alternatives here, not runtime-qualified integrations. Audit these existing systems before designing a custom journal implementation.

The contracts below describe what the chosen implementation must deliver. They do not prescribe writing it from scratch. Compare adoption, partial reuse and adaptation under the adoption method.

Three records with different purposes

Record Contents Use
Action journal Intent, action ID, parent revision, parameters, actor/session, time, outcome and committed revision. Explain changes, navigate history, undo and branch.
State and result store Checkpoints, raw/working datasets, models, fits, uncertainty results and exported figures, identified by hashes. Restore a known state and retrieve the exact saved result without recalculating it.
Execution log Job start/progress/completion/cancellation, warnings, failures and diagnostics linked to action IDs. Explain failed or interrupted work without pretending it produced a valid document state.

Recording a textual message is insufficient for undo. Every data-changing module must describe its input state and committed change, or provide a restorable checkpoint. Record navigation and presentation changes separately from measurement changes; a point drag can retain its gesture trace while committing one undoable data operation on release.

Undo, restore, rerun and branch

  • Undo: reverse a documented edit through the same command pathway. Preserve the original action and record the reversal; do not erase the audit trail.
  • Restore: open a materialized historical state, including the results that belonged to it. A stored result remains available even if its original software environment is unavailable.
  • Rerun: execute a calculation again with its saved inputs, model, settings and numerical environment. For Monte Carlo, record the random generator and seed too. A rerun creates a new result and can differ if the environment changes.
  • Branch: continue from an earlier revision while keeping the later history intact. Automatic merging of competing numerical edits is a separate, unqualified feature.

External effects need explicit semantics. Restoring an earlier state cannot retrieve a sheet already printed or undo an external transmission. Record the request and observed outcome; allow compensation only when the relevant adapter implements it. Exports can be retained as immutable artifacts with new versions instead of overwritten silently.

Reuse durable storage; define application semantics

SQLite transactions are a candidate for committing related state and journal metadata together. A content-addressed artifact store can retain large datasets and figures outside the journal rows. Git's object model is a useful reference for snapshots and parent links, and ordinary Git may version portable project files. Neither automatically defines undo for a fit or the meaning of a failed export.

SQLite's write-ahead log is a database mechanism, not the application's scientific history. Journal mode, backup and durability settings need qualification for the actual storage environment. The proposed application schema uses stable revision IDs, ordered parent links, versioned event types and explicit artifact references. Database/storage choice remains open.

Git and GitHub as available components

R22 requests these capabilities in the constructor. Retain and assess the existing Code - OSS implementation first: the pinned tree contains git-base, git, github and github-authentication extensions. The git and github manifests depend on git-base. Official VS Code guidance distinguishes basic Git operations from optional pull-request, issue and virtual-repository extensions.

Expose local versioning and the GitHub connection separately. Local commits and branches work without a hosting account. A remote connection adds transfer and collaboration; connecting an account does not itself synchronize unsaved work. The derivative's own authentication callback, credentials and transport require testing. This project's successful GitHub publication is evidence for its publishing setup, not proof of sign-in inside the generated app.

Offer Purpose and storage policy Current evidence
Local Git Named project checkpoints, diffs, branches and restoration. Link the commit to an application revision and portable journal export. Disposable CLI test passed commits, branches, local-remote transfer and fresh-clone restoration with artifact hash checks. Editor UI integration remains to be qualified.
GitHub connection Clone, fetch, pull and push selected project content. Display local-save, committed and remotely synchronized states separately. Pinned implementation and documentation inspected; generated-app authentication and error handling remain untested.
Large-file storage Use Git LFS or an external artifact store when appropriate, recording hashes and locations in the project manifest. LFS retrieval worked for the baseline build. Project artifact upload, quotas, availability and fresh-machine recovery remain to be qualified.

“Save everything” should mean all content needed to restore the chosen project state: data, models, settings, journal checkpoints, results, figures and environment records. Store selected portable files in Git; use Git LFS or another verified store for suitable large artifacts. LFS commits contain pointers, so a repository alone does not contain those artifact bytes. Verify recovery with the actual objects available. Credentials and disposable caches belong outside the project archive.

The action journal continues to record individual changes and failed jobs. A Git checkpoint should capture a consistent exported state and its artifact manifest, not an arbitrary copy of a live database and WAL files. A checkpoint action can link the document revision to the resulting commit without trying to store a commit hash inside the same commit. Before admission under R21, test conflicts, offline operation, failed pushes, sign-out, missing artifacts and restoration after a fresh clone. None of these offers implies a mandatory GitHub account for every app.

Required recovery experiment

  1. Edit a row, move a point, run a fit or a stand-in job, export a figure and record a deliberate error.
  2. Close the app and reopen it; recover the document, action history and saved artifacts.
  3. Restore an earlier checkpoint and create a branch; prove the original branch remains intact.
  4. Interrupt a job and simulate a crash during commit. Recover a complete prior or new state, without a half-recorded edit or a false successful result.
  5. Change an input while an old job finishes. Keep the old job's record, but do not attach its result to the new revision as current.
  6. Verify schema migration and restoration with an unavailable calculation module. Stored results must remain inspectable even when rerunning is unavailable.

This service should be designed before fitting and uncertainty adapters depend on it. In an app that selects durable provenance, all participating modules must honor its contract. See the component catalogue and the next construction steps.
