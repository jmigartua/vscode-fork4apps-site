Reuse components, compose capabilities

Reuse components, compose capabilities

Tables, graphics, fitting, uncertainty and publication output are families of optional tools. Reuse established implementations and build the document adapters that let selected tools work together.

The user's additions are recorded in R15–R18. The neutral workbench remains the starting example. These capabilities are offers for particular apps, not a compulsory scientific stack.

The optional fitted publication combination reuses these same SciPy and Matplotlib adapters. It exports the stored result without refitting, adding a residual panel and full JSON report. No additional plotting or optimization framework is introduced.

Separate the responsibilities

Import and quantitiesDocument and transformationsFitting and uncertaintyInteractive viewsPublication and reports

Each stage can contain smaller modules. A table might select editing, sorting, filtering or clipboard support. A plot might select scatter, error bars, image export or point editing. An app may need a publication renderer without a live plot, or interactive plots without Python. Dependency resolution must distinguish required shared services from optional tools.

Candidate implementations

Fitting SciPy; lmfit SciPy now supplies the bounded optional fitting adapter. lmfit remains a candidate for richer models; bounds and correlated errors are not admitted.

Publication figures and reports Matplotlib, PGF/LaTeX, the existing Quarto workflow Separate vector/raster output, mathematical typography and complete report composition. A simple plot export need not install a TeX distribution.

These are candidates, not a promise to ship every library. Selection weighs scientific requirements, editable data semantics, accessibility, performance, offline operation, bundle size and maintenance. Review licences for the exact versions and features selected; the experiment includes the MIT notices from its pinned Tabulator and Plotly packages. Other candidates have not been approved for redistribution by this evaluation.

A working, bounded reuse experiment

Open the interactive table-and-plot experiment. It uses synthetic data, Tabulator 6.6.1 and the Plotly.js basic bundle 4.1.2, served locally by the site with no CDN dependency. The small integration layer owns edits, stable row identifiers, shared undo/redo, snapshots and revision checks. It does not implement a new table renderer or chart engine.

Table edits and plot-point moves update both views and refresh a background mean calculation. Add/remove actions use the same document history. Select a point and enable plot editing to drag its orange handle; panning and zooming are separate. Edits commit on release. A removed row can be restored by undo. A future measurement app should distinguish correcting a derived working copy from overwriting immutable acquired data.

Browser checks exercise real interaction and snapshot reopening. Separate table-only and plot-only builds omit the unused renderer's files and network requests. Five model checks cover edit validation, shared updates, undo/redo, insert/remove and rejection of stale asynchronous results. This is a standalone browser experiment, not a Code - OSS extension, a new template 0.1 recipe or a performance qualification. The table experiment currently includes Tabulator's full bundle; smaller internal module builds remain to be evaluated.

Publication output from the same snapshot

Template 0.3 now offers an optional publication package integrated with the saved linked-data project. The earlier standalone experiment below remains its reuse baseline.

A separate Matplotlib adapter consumes a frozen snapshot and writes input/output hashes, source revision, row IDs and renderer versions beside the figure. Local checks produced PDF with Mathtext, PDF with LaTeX, and PDF/PGF with XeLaTeX. Their rendered pages were inspected. The supplied error bars are synthetic inputs; the exporter does not calculate their uncertainties.

Mathtext handles a subset of mathematical notation without installing TeX. LaTeX rendering needs an external toolchain; PGF provides a route into TeX documents and matching typography. These must be separate constructor choices. Data and semantic labels can be shared across renderers; identical typography and round-trip editing of every Plotly/Matplotlib option are not promised.

Fitting is a numerical capability

The app should record the selected rows, transformations, model, initial parameters, constraints, residual definition and uncertainty assumptions. Return parameters, covariance where justified, residual diagnostics, convergence status and the input revision. A curve on screen is a rendering of that result, not its authoritative storage.

SciPy's curve_fit distinguishes absolute supplied uncertainties from residual-based covariance scaling. The adapter must expose that choice correctly. Uncertainty in the horizontal coordinate may require an errors-in-variables method rather than ordinary vertical least squares. A parameter confidence interval, a fitted-mean band, a prediction interval and a measurement coverage interval must retain their own labels and assumptions. Bootstrap and MCMC posterior sampling are further methods; they are not interchangeable with Monte Carlo propagation of input distributions.

GUM and Monte Carlo need explicit measurement models

The standards register starts with the BIPM JCGM publications: GUM 100, its 2026 amendment on nonlinearity, Supplement 1 (JCGM 101) for Monte Carlo propagation, Supplement 2 for multiple outputs, and the guidance on developing measurement models. The 2026 amendment explicitly addresses nonlinearity; a library's name alone cannot establish that all these cases are covered.

Proposed qualification requirements:

  • Inputs: defined measurand and model, units, estimates, standard uncertainties or distributions, correlation/dependence information and provenance. Shared calibration effects must not be treated as independent noise for each point.
  • GUM adapter: a documented propagation method, sensitivity information, covariance handling, uncertainty budget and appropriate coverage treatment. Do not assume a universal coverage factor of two.
  • Monte Carlo adapter: sample the specified joint inputs; record the generator, seed, numerical environment, trials, convergence checks, invalid model evaluations and interval convention. The number of draws alone does not demonstrate accuracy.
  • Validation: compare with analytical cases and published reference examples; include correlated inputs, nonlinear models, degenerate covariance and failed fits. A production adapter must state its qualified scope.

The optional SciPy adapter now supplies two fitting models. GUM and Monte Carlo remain researched design candidates. The experiment's asynchronous mean only tests that a dependent calculation follows a data revision. Its scalar yerr column is deliberately insufficient for a general uncertainty model.

Adoption audit before implementation

The user's explicit R20 makes this the entry condition for each new capability: search, inspect, test a bounded example, then decide whether to adopt a whole component, reuse selected parts, adapt an existing system, or implement a missing piece. Innovation should address an evidenced limitation, with a comparison against the existing option.

Each audit must identify the exact version or source revision, licence and distribution conditions, maintenance evidence, dependencies, capability boundaries, data/host interfaces, tested scenarios, failure cases and remaining work. Documentation review is not runtime proof; a smoke test is not a full source, numerical or security audit. Do not combine every candidate into one compulsory stack.

When a candidate becomes a selectable option

R21 requires successful checks before admission. Record the exact version and host, verify dependencies and distribution terms, exercise the claimed behavior and failure cases in a generated app, and confirm that omitting the package leaves the neutral app working. Scientific adapters additionally need reference-case tests; durable history needs restart and interrupted-commit recovery.

Promote only the scope that passes. Failed, incompatible and untested combinations stay outside the supported recipe registry. Keep their findings in this research catalogue so they can be corrected and retested. Template 0.2 now admits the combined linked-data editor for its tested saved-checkpoint workflow. Other candidate combinations remain outside the supported registry; automatic unsaved crash recovery failed admission.

What the constructor should own

Maintain a capability registry, compatible library versions, dependency and licence records, small adapters, document contracts and qualification tests. The skill should first search this catalogue, explain the selected combination and identify missing contracts. The optional custom-editor package now implements the bounded linked-data workflow. Publication and the first fitting adapter now have bounded qualifications; uncertainty adapters remain open. See the construction roadmap.
